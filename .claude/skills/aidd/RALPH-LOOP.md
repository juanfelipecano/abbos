# The Ralph Loop — Execution Mechanics

How work actually gets ground through, once a spec exists. Named after Geoffrey Huntley's
technique: run an agent in a loop until the work is done, with every iteration starting
from zero memory.

The core insight is counterintuitive. The loop is not powerful because the agent remembers
more — it is powerful because the agent remembers **nothing**, and is therefore forced to
re-derive its state from files that are actually true. Context rots. Files do not.

---

## The loop

```
0. LOCATE     Read .aidd-active → the active feature slug.
1. ORIENT     Re-read from disk: PROJECT-CONTEXT.md, specs/<feature>/spec.md,
              specs/<feature>/plan.md. Never from memory. Never "as established earlier."
2. SELECT     Take the single highest-priority unchecked task. Exactly one.
3. IMPLEMENT  The minimum change that advances that task. Nothing adjacent.
4. VERIFY     Run the project's verify command. Non-zero exit is a hard stop.
5. RECORD     Check the task off in specs/<feature>/plan.md. Commit atomically.
6. ITERATE    On failure: exact diagnosis → minimum adjustment → back to 3.
              Three failures on one task → STOP and escalate.
7. DONE       Every criterion green → report with evidence.
```

Steps 1 and 5 are the ones people drop, and dropping them is what turns the loop into
thrashing. Step 1 is how the agent survives context compaction. Step 5 is how the *next*
iteration survives it.

---

## Why each rule exists

**One task per iteration.** A small commit is individually reviewable and individually
revertible. Ten tasks in one commit means one bad task costs you the other nine, and the
reviewer cannot tell which change caused the failure.

**Progress in files, not context.** After compaction, an agent's recollection of "what's
left" is a summary of a summary. `specs/<feature>/plan.md` on disk is the real answer. This
is Article VII, and it is the single highest-leverage habit in the method.

**Guardrails as backpressure.** Tests, linters, and type checks are not quality theater —
they are the mechanism that stops a broken change from becoming the foundation of the next
one. The agent must not proceed past a red check. In a supervised session that means "fix
it now"; in an unsupervised loop it means the iteration exits without committing.

**Three-strike cap.** An agent that has failed the same task three times is not one guess
from success — it lacks information or the design is wrong. Attempt four spends budget to
re-confirm attempt three. Escalate with the three diagnoses; that transcript is what makes
the human's or architect's decision fast.

**Sit on the loop, not in it.** Do not supervise each iteration. Define the target, tune
the guardrails, and read the git log. When output is wrong, fix the *instruction* — the
spec, the project context, the skill — not the artifact (Article XII). Otherwise you are
the loop's bottleneck and you have automated nothing.

## Plan mode and build mode

Keep them strictly separate. An agent that plans and builds in the same pass will bend the
plan to match whatever it already wrote.

**Plan mode** reads every spec and the existing code, performs gap analysis, and writes
`specs/<feature>/plan.md`. It changes no code. Owned by `aidd-planner`.

**Build mode** reads the plan, executes the top task, verifies, commits, and stops. It
does not re-prioritize and it does not add tasks. Owned by `aidd-implementer`.

If build mode discovers the plan is wrong, it does not fix the plan. It escalates — the
plan's author owns it (Rule 6).

## Where state lives

Three paths, and the relationship between them is the whole layout.

```
.aidd-active                  one line: the active feature slug
specs/
  csv-export/
    spec.md                   the frozen contract
    plan.md                   the loop's state file
  scheduled-exports/
    spec.md                   a second feature — no collision
    plan.md
```

**`.aidd-active`** is the single known entry point. One line, no formatting:

```
csv-export
```

Without it, a session resuming after a compaction has to guess which feature is in flight —
and guessing is precisely what the plan file exists to prevent. It is the only file at the
root, and it holds a pointer rather than state.

**`specs/<feature>/plan.md`** is the loop's state file, generated by the planner, updated by
the implementer, and read at the start of every iteration.

Plans are **never archived or moved.** A closed run's plan stays next to the spec it
implemented, attempt log intact — that log is what answers "why was this built this way"
a year later. Starting a second feature creates a second directory; nothing is overwritten,
because nothing shares a path.

### The plan file

```markdown
# Implementation Plan — <feature>

Spec: specs/<feature>/spec.md
Iteration: Iter-1
Status: planning | executing | escalated | DONE
Verify: <the project's verify command>

## Tasks

- [x] 1. <task> → <files touched> → verified by <check> — commit a1b2c3d
- [ ] 2. <task> → <files> → verified by <check>          ← NEXT
- [ ] 3. <task> → <files> → verified by <check>          (blocked by 2)

## Attempt log

| Task | Attempt | What I changed | Result |
|---|---|---|---|
| 2 | 1 | <change> | <exact error> |

## Escalations

<none, or the escalation report>
```

Each task must be **atomic** (one commit), **verifiable** (a named check, not "looks
right"), and **ordered** (dependencies explicit). A task nobody can verify is not a task —
it is a wish, and it belongs back with the planner.

## Running it for real

Three ways, in increasing autonomy. All three obey the same rules; they differ only in how
much a human is present.

**Supervised — one iteration per turn.** The default. Ask for the next task, review the
commit, continue. Best while the spec is still proving itself.

**Self-paced with `/loop`.** In Claude Code, `/loop` re-invokes a prompt on an interval or
lets the model pace itself:

```bash
/loop Read .aidd-active for the feature slug, then specs/<slug>/plan.md. Execute the single next unchecked task per the aidd-implementer skill, verify, commit, update the plan. Stop and report if a task fails 3 times or the plan is complete.
```

**Unsupervised — the original shell loop.** Headless, for well-specified mechanical work
with strong automated checks:

```bash
while :; do cat PROMPT_build.md | claude -p --dangerously-skip-permissions; done
```

Only run this in a container or disposable worktree, on a branch you are willing to throw
away, with a hard iteration ceiling and a real verify command. Without those four things it
is not autonomy — it is an unsupervised process with commit access.

`PROMPT_build.md` is a thin wrapper, because the discipline lives in the skill files:

```markdown
Read .aidd-active to get the active feature slug.
Read PROJECT-CONTEXT.md, specs/<slug>/spec.md, and specs/<slug>/plan.md from disk.
Follow the aidd-implementer skill.
Execute exactly one task: the highest-priority unchecked item.
Run the verify command. If it fails, fix it; do not commit red.
Update specs/<slug>/plan.md, commit atomically, then exit.
If all tasks are checked, set Status: DONE in the plan and exit.
If any task has 3 logged failed attempts, write the escalation report and exit.
```

## When not to use the loop

Ralph converges when the target is unambiguous and machine-checkable. It does not converge
otherwise, and forcing it wastes real money.

**Good fit:** greenfield work from a clear spec, repetitive mechanical changes across many
files, migrations, test backfill, anything with a strong existing test suite.

**Bad fit:** vague requirements — do the specification work first, that is what the analyst
and PM roles are for. Subjective or aesthetic judgment. Domains with no automated
verification. Changes to the boundaries listed in `PROJECT-CONTEXT.md`.

The honest test: *can a script tell me this task is done?* If no, the loop cannot either,
and you need a human gate at that step.
